Terraform Agent

An LLM/VLM agent that turns a text prompt or a reference photo into a Minecraft landscape 256 blocks across. It plans a feature graph, builds on an in-memory terrain canvas through semantic tools, looks at renders of its own work, gets critiqued by a separate model call, and is kept or rolled back by an acceptance gate. The final canvas is compiled into a real Minecraft 26.3 world.

The pitch

"I built my own agent runtime, not a prompt on top of an API. The model owns intent and taste; code owns precision. The model never places blocks: it calls about 20 semantic tools like raise_ridge(path, width, height, character), and every call is an entry in a replayable op stack, so undo and revision are just edits to that list."

"Each run writes a feature graph first, which becomes a checklist that code measures. A fresh-context critic adds located, schema-checked fixes. An acceptance gate decides what to keep using objective checks first and a blind, order-randomised comparison second, because absolute LLM scores were too noisy to gate on. I can show the trace that made me change that."

"Every change goes in an evidence log with traces and numbers, including the experiments I reverted."

Positioning versus related work (DESIGN §17): Minecraft agents like Voyager or MCP block servers act block by block or pick preset generators, with the loop in a generic client. This project treats terrain as a canvas of semantic, replayable ops, with features as the unit of planning and checking, and has its own runtime, critic and evaluation. SceneCraft (scene graph + VLM reviewer), 3D-GPT (LLM picks procedural parameters), TIFA/DSG (atomic checklists) and SWE-agent (the agent–computer interface matters) are the closest ancestors.

DESIGN §3–§11, agent/ and terrain/

Architecture

model call deterministic code user input / Minecraft world dashed = state or data flow, not a call

Agent runtime

harness.py runs the outer BUILD → CRITIQUE → keep/rollback loop and the inner tool loop. context.py decides what the builder sees. budget.py and tracing.py stop runaway runs and record everything.

Model adapter

models.py: one complete() interface for builder, SPEC, critic and comparison. Anthropic first, price table, prompt-cache breakpoints, structured output. A fake adapter drives the tests.

Tool layer

tools.py turns every registered op into a tool. Agent-fixable failures (OpError) become is_error tool results; any other exception is a bug and crashes loudly.

Canvas

The source of truth: WorldState arrays plus an ordered op stack plus a feature registry. Ops are pure functions, state in, new state out.

Output

Renders are views of the canvas. The world is compiled from it, diffed against what is there, and written through a swappable backend.

A real run: traces/20261023-151207-d09ebc.jsonl · Haiku 5.5 · 3 rounds · L2 renders

One prompt, end to end

This is the M5 text milestone. Everything below is what the trace recorded, lightly trimmed. The prompt was "a valley between two rugged mountains, a lake in the middle and a river flowing to the south edge".

  1. code · agent/run.py

    Wire up the run

    Session.flat(256, 256, base_y=64) creates an empty canvas. The tool dict is built from the op registry plus list_ops, update_op, remove_op and render_view; the harness adds write_note. A step-0 trace header records the prompt, image hashes, models, budget, canvas, git commit with a dirty flag, and a SHA-256 of the tool list, so a run can be reproduced or re-scored from its trace alone.

  2. model · SPEC call

    Write the feature graph

    One call in a fresh context, constrained to the FeatureGraph JSON schema. Pydantic validates it, then problems() checks what the schema can't (1–15 features, id format, references). An unusable reply is retried once; a second failure builds from the raw prompt without a checklist, and the trace says so.

    features: mountain_west (peak, x=left)   mountain_east (peak, x=right)
          valley_1 (valley, x=center)    lake_1 (lake, center/middle)   river_1 (river, anywhere)
relations: valley_1 right_of mountain_west · valley_1 left_of mountain_east
           river_1 reaches south_edge

    Note what is absent: the river has no position because the prompt only says where it ends. That rule came from a spot check where the SPEC call invented positions and relations (EVIDENCE 2026-10-23).

  3. code · agent/spec.py

    Project to the canvas and pin it

    Qualitative positions map to (u, v) bands with built-in overlap as one category of slack: left → u 0–0.45, center → u 0.25–0.75. The viewer stands at the south edge looking north. spec_text renders the request plus each feature with its band; it is pinned into every builder episode, the critic and the comparison. The session learns the spec's feature ids, so tagging an op with an unknown feature is an error.

  4. code · agent/context.py

    Open episode 1

    The builder gets the system prompt and tool schemas (fixed for the run, so they hit the prompt cache) and one opening message built from state: task, spec with bands, terrain stats, "(no ops yet)", notes, latest renders. History is never edited; each round starts a fresh conversation.

  5. model · builder, inner loop

    Build large forms first

    raise_peak   {"center":[0.15,0.5], "radius":0.38, "height":90, "character":"rugged",
              "feature":"mountain_west", "id":"mountain_west"}
→ applied mountain_west: footprint u=0.00..0.48, v=0.14..0.93, y=64..154;
  top y=154 at (u=0.15, v=0.50); slope max 78°, mean 45°; 15,857 columns.
  Terrain now: area 256x256 blocks; height y=64..154 …

    Then the mirror peak, carve_valley down u=0.5 (width 0.3, depth 40), a basin with raise_region(mode="basin"), and fill_lake. Every op carries feature= so the checklist can measure it.

  6. code · one tool call, inside

    What a single call does

    1. execute() looks up the tool; an unknown name returns an error listing the real ones.
    2. Session.apply checks the feature tag, takes a checkpoint, and runs the edit under the guardrail: more than 40 blocks of height change per column on average is undone with "narrow the region, or lower height".
    3. OpStack.add validates params with the op's pydantic model (unknown fields rejected), assigns an id, and either applies incrementally (latest stage) or replays the whole stack.
    4. apply_op runs the pure op on a copy, seeded with crc32(f"{base_seed}:{op_id}"), then checks world height limits with a fix amount ("reduce it by at least 22 blocks").
    5. The height/water diff becomes the op's footprint mask and feature record; tagged ops also grow a spec:<id> union mask.
    6. The result string reports footprint, summit, slopes and columns, so the model never needs raw arrays.
  7. model · observe and self-correct

    The lake leaked; the builder saw it

    The fill_lake result said its footprint ran to v=1.00: the basin spilled down the open valley to the south edge. The builder called render_view(map), then remove_op("lake_fill"), added a dam (raise_region polygon, +22 blocks across the valley at v≈0.65), and refilled. The new footprint stopped at v=0.60.

    This is the case for informative tool results. Nothing failed, but the stats in the result made the physical mistake visible, and remove_op made it cheap to undo.

    It then carved river_1 from the lake to the south edge, checked a 3D view, ran hydraulic erode, set a palette, wrote a note, and ended its turn with a summary.

  8. code, then model · critique round 1

    Checks, checklist, rubric

    Programmatic checks ran first (all passed), then the spec checklist (all passed), then one critic call with the L1 map and L2 voxel render. Score 3.20, verdict revise. Top issues, each with a tool and parameters:

    • major valley_1 walls are bare grey stone → set_palette_rules
    • minor river_1 sinuosity 1.03, dead straight → update_op river_1: meander=…
    • minor mountain_west is a symmetric blob → update_op mountain_west

    Round 1 is accepted as the baseline: there is nothing to compare it with.

  9. model · round 2

    Revise with update_op, not new ops

    A fresh episode built from state plus the critique. The builder replaced the palette, called update_op river_1 {"meander": 0.5} and update_op mountain_west {"irregularity": 0.75}. Critique: 3.60. Gate: no check regressed, the checklist count was equal, and the blind comparison said "same", so the revision was kept (ties keep the revision).

  10. model · round 3

    Targeted fixes

    The builder scoped a palette rule to feature: valley_1 and added a ridged, relief-weighted roughen on mountain_east. The blind comparison preferred the revision ("more irregular, jagged relief"). The round limit ended the run on round 3. The three runs in this batch cost $0.07 together.

  11. code · save_final

    Persist the result, even on a crash

    In a finally block: renders/<run_id>/stack.json first (so it survives a render failure), then final_l1.png and two L2 views. The session is already restored to the latest accepted attempt.

  12. code · compiler and backend

    Compile into Minecraft

    python -m scripts.compile_world --world <world dir> --stack renders/<run_id>/stack.json

    OpStack.from_json replays the stack deterministically. compile_state rounds heights to blocks (only here), picks the surface block per column from the palette rules, extends rock down exposed cliff faces, adds subsurface layers and stone, and re-contains water after rounding. build_patch reads the world's current surface, compiles over a y range covering both, and diffs: only changed blocks are written, and the patch doubles as the undo record. AmuletBackend refuses a world whose session.lock is held, writes to a copy, writes sky light for changed chunks, swaps it in, and keeps the old world as a snapshot. This build sits in TerraformTest at (1200, 300), snapshot 0023.

DESIGN §9, §13 · agent/harness.py, agent/context.py

The harness loop

Grown from a port of Thorsten Ball's "How to Build an Agent", with no agent framework. Two nested loops and a context manager. The value of writing it by hand is that every stop reason, retry, budget and context decision is explicit and traced.

Inner loop: run_stage

Model call → run tool calls → feed results back, until the model ends its turn, a budget stops it, or it refuses. It switches on stop_reason explicitly:

stop_reasonhandling
tool_useRun each call; errors come back as is_error results. A non-OpError exception is traced with the calls that caused it, then re-raised.
end_turnStage done; go to critique.
max_tokensTruncated tool calls are not run; ask for a re-issue.
pause_turnResend as-is so the model continues.
refusalStop the stage and record why.
anything elseRuntimeError: fail loudly.

Outer loop: run_task

  1. SPEC (or a given graph, or --no-spec).
  2. For each round up to max_rounds: render, build an episode from state + the accepted attempt's critique + rollback feedback, run the inner loop.
  3. Snapshot the canvas, critique it.
  4. Round 1 is the baseline. Later rounds go through the gate: keep, or session.restore(accepted) and remember the op diff and the reasons.
  5. A "pass" verdict on a kept attempt ends early; so does a spent budget.
  6. Always finish on the latest accepted attempt.

Budgets: model calls (builder + critic together, default 40), USD (default $2) and wall time (900 s), checked before every model call. Failed critic calls are still charged.

Context: episodes, not history edits

Current Claude models bind thinking blocks to the conversation, so dropping old renders or summarising earlier turns would invalidate it. Instead each round opens a new episode whose first message is generated from state. Inside an episode history is append-only. When an episode passes 150k input tokens or 80 messages, the harness rotates: tool results are already applied to the session, so a fresh episode built from state loses nothing.

This is cheap because the op list is the memory. The chat is disposable. Only write_note notes carry model-written context across episodes.

Cost control

  • System prompt and tool list are byte-stable for the run: deterministic tool order, no timestamps. The adapter puts an explicit cache breakpoint at the end of the system prompt, because the automatic one at the end of messages never matches across episodes.
  • Images dominate input cost: fixed sizes, only the latest renders in the opening message, render_view capped at 12 per run and refused on unchanged terrain.
  • Programmatic checks run before any critic call; a blocking failure skips the model call entirely.
  • One semantic call replaces thousands of block edits; update_op replaces stacked fixes.
DESIGN §5.1, §5.9 · agent/tools.py, terrain/ops/registry.py

How the builder finds, picks and uses a tool

Be precise about this in an interview: there is no tool retrieval and no tree search. All 20 tools are in context every call (15 ops, 3 control, render_view, write_note), and the model picks through native tool use. The engineering is in making that choice easy and the feedback sharp. The "search" across solutions happens in the outer loop: a greedy hill-climb over attempts with an acceptance test and rollback.

1. How tools reach the model

  • Each op is registered with @register_op(name, params=Model, stage=…). The pydantic model is the validator and the JSON schema; the function's docstring is the description. One source, so they can't drift.
  • op_tools() adds two shared optional fields to every schema: id (name the op for later update_op) and feature (the spec feature it builds).
  • Tools are sorted by stage then name, so the list is identical byte for byte across calls.
  • A test fails if any schema exposes a raw algorithm knob (octaves, iterations, angles, rates).

2. What steers the choice

  • Descriptions written as intent, with when-to-use and ordering: raise_ridge says "finish a range with erode (hydraulic), then a small ridged roughen, then the palette".
  • Schemas that constrain: enums (profile: v | u), 0–1 ranges, presets (gentle … jagged).
  • The pinned spec with (u, v) bands, so placement is a lookup, not a guess.
  • Critic issues with a structured fix (tool, op_id, changes), validated against the schemas before the builder sees them.
  • Checklist hints that name parameters: "raise meander on its carve_river op (0.3 = winding, 0.6 = twisty, 1.0 = meandering)".

3. How a call is used

  • The model emits tool_use; execute() dispatches it. Validation, guardrail, world limits and replay happen in code (see step 6 of the walkthrough).
  • Every result states what changed: footprint, summit, slopes, water, plus whole-terrain stats. Materials ops say "surface blocks only" so the model doesn't think nothing happened.
  • Errors say what is wrong and by how much, and the edit is all-or-nothing, so a failed call leaves the canvas unchanged.

4. How it revises

  • update_op(id, params) merges new params and replays the stack. Values derived from a preset are re-derived (stale_on_update).
  • remove_op is undo; it is never limited by the guardrail.
  • Because each op's seed comes from its own id, editing one op never reshuffles another op's noise.
  • Stages fix replay order (terrain → water → materials), so a later erode can't erase an earlier river.
Why no tool retrieval: at 20 tools the whole list costs a few thousand cached tokens, and DESIGN §5.1 forbids overlapping tools, which is the main reason retrieval helps elsewhere. If the catalogue grew past ~50 (vegetation, 3D sculpting, structures), the natural next step is grouping by stage and loading a stage's tools when that stage starts, which the stage field already supports.
DESIGN §4, §9.3, §11.3, §12 · agent/spec.py, agent/checklist.py, terrain/features.py

The spec graph and features

Principle 3: features, not pixels. A feature is a named landform the builder, critic and checklist can all talk about. The LLM speaks in categories; code owns the numeric ranges and measures them.

FeatureGraph schema

SpecFeature: id, type (peak | mountain_range | hills | ridge | valley | canyon |
             river | lake | sea | plateau | mesa | basin | island | other),
             position {x,y} (text) or {image_x, depth} (photo),
             span_x / span_y: narrow | wide | full,
             slope: gentle | moderate | steep | cliff,
             winding: almost straight | winding | twisty | meandering,
             tallest, part_of, notes
Relation:    left_of | right_of | behind | in_front_of | taller_than |
             lower_than | flows_from | reaches  (feature or an edge)
+ materials (one sentence) + unsupported (mist, trees, buildings …)

The schema has no numeric or length constraints because structured outputs reject them; problems() enforces those in code.

From photo to map

VLMs order depth reasonably but are poor at metric distance and at projecting perspective to top-down. So the SPEC call describes a photo in image terms (image_x: center-right, depth: far) and code projects with a fixed camera at the south edge: depth → a v band; image_x → a u centre spread by the frame width at that depth (near 0.5, middle 0.75, far 1.0 of the area). Text and images share one graph, one builder and one checklist.

Features from ops

After every op the stack diffs height and water; the changed area becomes features[op_id] with bounds, top/bottom y, column count and a soft footprint mask (weight ∝ |Δh|). Ops don't need to know their id.

Ops tagged feature="river_1" map a spec feature to op ids. measure_spec_feature measures over the union of their footprints, on the body (weight > 0.5):

  • Prominence: classic topographic prominence from one union-find pass over the heightmap.
  • Sinuosity: recomputed from the exact centre line carve_river cut (same params and seed).
  • Slope class: mean slope, except for wall-defined types (plateau, mesa, canyon, valley, basin), which use the 90th percentile. On the mesa demo the mean says 26° (moderate) for a sheer mesa; p90 says 77° (cliff).
  • Extent, centroid, source and mouth, edges touched.

The checklist

The graph becomes atomic items, in the style of TIFA and the Davidsonian Scene Graph:

  • <id>.exists. If it fails, the feature's other items and relations are skipped, not failed.
  • .position: centroid in the band. .span_x/y, .slope, .winding: one category of slack (one off = minor, two = major).
  • .tallest, excluding the feature it is part of and its own parts.
  • Relations with margins: centres ≥ 0.05 apart, summits ≥ 2 blocks apart, river source within 3 blocks of its feature, mouth within 2 blocks of the edge.

Failed items carry a directional hint (steeper vs gentler, more vs fewer bends). Any failed major item forces "revise", and the pass count is gate rule 2.

DESIGN §11.1–§11.5 · agent/critic.py

The critic

Self-refinement grounded in tools: unaided LLM self-correction is unreliable (Huang et al.), tool-grounded critique works better (CRITIC). The critic never sees the builder's conversation. It judges and suggests; the builder decides; the harness accepts or rolls back.

The model call

Inputs: spec, reference images, L1 + L2 renders, terrain stats, the measured feature report, the op list, the checklist, the palette in use and the check results. Output is strict JSON with issues before scores, so the model reasons before it rates.

Rubric 1–5: prompt_adherence, layout, naturalism, minecraft_quality, materials, reference_match (null without a photo). "Pass" only with no major issues and every score ≥ 4; code overrides to "revise" on any failed major check or checklist item.

Fixes the builder can execute

Each issue has a location (op id or u,v), a tool (an op, update_op, remove_op or "none"), an op_id, and changes as param/JSON-value pairs. A generated tool catalogue in the critic's cached system prompt lists every op with allowed values and ranges and the palette rule format. hint_problems() validates each fix against the real pydantic fields. tool: "none" issues are a ranked list of missing tools (scripts/missing_tools.py).

DESIGN §11.4 · harness._gate

The acceptance gate

Rules, in order

  1. rule 1Roll back if the revision fails a blocking or major check the accepted attempt passed.
  2. rule 2Checklist count, symmetric: fewer passes roll back; more passes keep the revision with no comparison; equal goes on.
  3. rule 3Blind comparison: "Terrain 1" vs "Terrain 2" in a seeded random order (Random(seed·1000 + round)), renders with neutral titles and stats only, no op lists, no previous critique. Symmetric output: strengths of each, then better: 1 | 2 | same. Only a win for the old attempt rolls back; ties keep the revision. --compare-both-orders needs agreement.
  4. rollbackRestore the checkpoint; the next episode gets the op diff (added, removed, old → new params), the reason and the rejected attempt's issues: "try a different fix".

Why it looks like this

The first version gated on "mean rubric score higher than the best so far". The M3 baseline trace rolled back a revision that had addressed the critique because it tied 3.00 = 3.00. Re-scoring 27 decisions later: 11 revisions tied exactly, and the score gate would have thrown away 12 revisions the new gate kept.

An in-call "previous vs revision" framing was also rejected: models favour whatever is framed as the improvement. Hence blind, symmetric, order-randomised.

Validation: 9 Haiku runs × 4 rounds, 25 comparisons: revision wins 36%, previous 20%, same 44%. "Terrain 1" won 57% of 14 decisive verdicts, so no position-bias flag. A constructed test (valley vs a broken copy) picks the intact one in both orders. Rule 2 became symmetric after a run where a revision fixed a spec item (5/7 → 6/7) and the comparison still rolled it back: objective evidence now outranks the model's preference.

DESIGN §3, §5.4, §7, §8, §10

Canvas, compiler and backend

Canvas and op stack

  • WorldState over W × D columns, arrays indexed [z, x]: float32 height, int16 material (0 = auto), water surface (NaN = dry), named float masks, and the feature registry.
  • replay(stack) is deterministic. Entries run grouped by stage, insertion order within a stage.
  • Appending to the latest stage applies to the cached state; any other edit replays. Every edit is all-or-nothing and errors name the op id.
  • Checkpoints are immutable (entries, state copy) pairs, used by the gate.
  • Brushes: almost every op is mask × falloff × shape × blend, with distances in blocks and blend modes add / max / min / lerp / smooth. Ops never convert coordinates themselves.

Compiler, backend, renders

  • Heights become blocks only in the compiler. Surface block from the palette rules, extended down exposed cliff faces so walls show rock; subsurface layers; stone below. Water is re-contained after rounding: lowered, never raised.
  • WorldBackend: read_region, apply_patch, snapshot, restore. A memory backend for tests; the Amulet backend (amulet-core 1.9.49, pinned) for real worlds.
  • Amulet drops light data and 26.3 may not relight, which made terrain above ~y 95 dark. The backend writes vertical sky light for changed chunks itself.
  • L1: matplotlib hillshade with contours, grid, north arrow and scale. L2: PyVista voxel preview, visible faces only, baked per-face shading, colours from a table measured from the local client jar (numbers only, no textures committed).

Failures found in traces, and the fixes

The tie that threw away a fix

Saw
Baseline run: a revision that addressed the critique was rolled back because 3.00 ≤ 3.00.
Did
Replaced the score gate with check regressions + a blind, seeded-order comparison; ties keep the revision.
Result
On 27 decisions, the old gate would have discarded 12 revisions the new one kept. Revision win rate 36%, not ~100%, so the comparison isn't just rubber-stamping.

The critic invented missing tools

Saw
Critic fixes named non-existent params, or said "no tool can do this" for things warp or a polygon region can do.
Did
Generated a tool catalogue for the critic; replaced free-text hints with a structured fix checked against the schemas; added an op_id field.
Result
Controlled A/B on 13 saved terrains: false "no tool" claims 6 → 1; valid fixes 47/47 after op_id. A text-heuristic checker was tried first and reverted.

Materials fixes were 11 of 14 invalid

Saw
Adding a materials score made the critic suggest palettes, written as prose or invented formats, and "rules 2–4 unchanged" because it never saw the palette.
Did
Generated the rule format into the catalogue from the pydantic models; showed the palette in use.
Result
Palette fixes 10/10 valid; all structured fixes 40/40.

Cones where the photo had ranges

Saw
Image build of valley1.jpg: checklist 16/16, but ranges were built as cones. The spec had no way to say "spans the frame", and the critic could only suggest cone-sized fixes.
Did
Added raise_ridge and span_x/span_y with checklist items; reworked the ridge to match a reference range recipe measured from the world.
Result
The builder used raise_ridge unprompted. Lesson: a checklist that measures "what and where" can pass while likeness fails.

A slope check that missed walls

Saw
A synthetic terrain with 20-block walls every other column measured 3.1% steep with np.gradient and passed.
Did
Central differences compare a column's two neighbours and skip the column itself; switched to per-block drop to any 4-neighbour.
Result
Demos 0.2–10.4%, the broken valley 81%; the 25% limit separates them.

Top-down maps hid 3D problems

Saw
In game, a kept valley had ~77° rim walls and bare stone; no L1-only critique ever mentioned it.
Did
Made the L2 voxel render the default for critique and comparison.
Result
New issue types appeared only with L2 (banding rings, hard steps, U-vs-V shape) at ~+30% critic input tokens. It also exposed a misattribution: the "rings" were the banded cliff palette, which led to the palette rework.

A tallest peak that could never pass

Saw
snow_peak.tallest compared the peak with its own range, whose footprint contains it; the builder kept raising it into a smooth white "egg".
Did
"tallest" now skips the feature it is part of and its own parts; test added.
Result
A reminder that a wrong objective check does more damage than a noisy subjective one: the agent optimises it faithfully.

Half-open polygons

Saw
A whole-area raise_region left 37 of 192 east-edge columns unraised, and a valley cut into them.
Did
The even-odd test was half-open; polygons now include edges on every side.
Result
8 tests at several sizes; 6 fail with the fix disabled. The island demo had worked only because its float edge distances happened to be exactly 0.

Gaps, risks and review findings

Project-level gaps

  • high No benchmark yet (M6). There is no evidence that SPEC or the critic improves builds on average; every result so far is N = 1–13, single-sample, Haiku only. Don't claim quality gains in a resume bullet until the ablations run.
  • high Builder and critic share a model. The blind comparison fixes recency and position bias, not self-preference. A different-family critic is designed but needs a second adapter.
  • med Layout passes, likeness doesn't. The checklist measures what and where; reference_match moved 2 → 3 → 2 across rounds. SPEC under-reads extent from photos (a full-width range came out "wide").
  • med Overlapping footprints share measurements until the dominant-feature map exists.
  • low Calibration sweep verdict and in-game demo checks not recorded; no README or before/after images yet.

Code review findings

  • med Uncommitted work: the raise_ridge rework and the "tallest" fix (7 files, tests pass) sit in the working tree. The working agreement says commit when done.
  • low agent/harness.py module docstring is stale: it says "the SPEC step comes in M5 … the spec is the prompt".
  • low CritiqueResult.score docstring in agent/critic.py still says "used for score-gated acceptance"; the score is reports-only now.
  • low Budgets are checked before each call, so one expensive call can overshoot the cost cap. Fine at Haiku prices; worth a per-call estimate for Opus eval runs.
  • low Rotation keys off the last call's input tokens; a burst of large tool results inside one turn is only caught on the next call.
Practise out loud

Likely interview questions

Why not let the model write terrain code directly?

Fixed tools enforce invariants in code (rivers descend, water fits rounding, height limits), make every edit replayable and revisable with update_op, cost fewer tokens, and give a stable interface I can evaluate and improve from traces. Code-as-action is planned as a sandboxed escape hatch, and each use is a signal for a missing tool.

How do you know the critic helps?

Honestly, not yet at benchmark level; that's M6 (critic on/off and SPEC on/off ablations against hand-written expected graphs, scored by a judge prompt separate from the critic). What I do have: gate statistics showing the comparison isn't biased toward revisions, a broken-copy test it passes in both orders, and A/Bs on the critic's fix validity.

How do you handle LLM-as-judge bias?

Objective checks and the checklist decide first. The comparison is blind (no op ids, neutral render titles, no previous critique), order-randomised with a recorded seed, symmetric in its output, ties keep the revision, and an optional both-orders mode requires agreement. I monitor revision win rate and "Terrain 1" win rate from traces.

What happens when the model returns garbage?

Tool calls: schema validation with agent-readable errors, all-or-nothing edits, JSON-string params tolerated for update_op. Truncated tool calls are never executed. SPEC, critique and comparison: strict JSON output, retried once, then a defined degraded path (no checklist; checks-only round; counts as a tie). Failed calls are still charged and traced.

How do you manage context and cost?

Byte-stable tools and system prompt with an explicit cache breakpoint; episodes rebuilt from state instead of growing history; rotation at 150k tokens or 80 messages; fixed image sizes and a view cap; checks before model calls; budgets on calls, dollars and time. Typical Haiku runs cost $0.02–0.04.

How do you test an agent?

Three layers. Ops have invariant tests (river bed never rises, lakes don't float, no 1-column pillars, no raw knobs in schemas). The harness runs against a fake model adapter that scripts responses, covering stop reasons, retries, rollbacks and gate rules. Live behaviour is checked from traces with scripts (gate_stats, gate_check, catalogue_ab, missing_tools) and logged in EVIDENCE.md.

Why a feature graph instead of just the prompt?

It turns a vague request into atomic, measurable items, gives the builder placements as (u, v) bands, lets the critic and checklist talk about named features, and gives text and photos one shared format. The fallback, if the ablation shows no gain, is to keep the graph only as the checklist and eval target.

How would you scale to many more tools?

Group by stage and load a stage's tools when it starts (the stage field already exists), keep the no-overlap rule, and use trace signals: wrong tool picks, repeated errors on one tool, parameters pinned at an extreme, the same multi-call sequence every run (a missing macro).

What would you build next?

The M6 benchmark and ablations first, because every later choice should be picked by benchmark failures. Then a different-family critic, annotated L1 renders (Set-of-Mark style labels) so issues are located by feature id, and a stronger photo-extent reading in SPEC.
